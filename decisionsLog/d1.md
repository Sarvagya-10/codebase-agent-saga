## Decision 001 — Repository Selection

**Decision:**  
Use the open-source repository **pallets/flask** as the target codebase for the Codebase Agent.

**Status:**  
Locked (non-reversible for this campaign)

**Date:**  
2026-01-02

---

### Context

This project requires a real-world Python codebase that:
- Exposes a meaningful public API
- Is large enough to stress retrieval and chunking
- Is small enough to be processed within tight time and compute constraints
- Uses idiomatic Python suitable for AST-based analysis
- Provides strong external credibility as a demonstration artifact

The repository will be used end-to-end for:
- AST-based semantic chunking
- Embedding and vector storage
- Retrieval-Augmented Generation (RAG)
- Documentation synthesis
- System-level evaluation under constraints

---

### Alternatives Considered

1. **psf/requests**
   - Pros: Very clean function-level APIs, low AST complexity
   - Cons: Limited architectural depth, fewer cross-file interactions

2. **tiangolo/typer**
   - Pros: Modern Python, rich type annotations
   - Cons: Higher AST complexity due to decorators and typing, increased implementation risk under time constraints

3. **pallets/flask**
   - Pros: 
     - Clear and widely-used public API
     - Medium-scale codebase suitable for local embedding
     - Idiomatic Python with minimal metaprogramming
     - Documentation-relevant abstractions (request lifecycle, routing, app context)
     - Strong external credibility and recognizability
   - Cons:
     - Some implicit behaviors not immediately obvious from single-file inspection

---

### Decision Rationale

**pallets/flask** provides the best balance between:
- Technical challenge and feasibility
- Architectural richness and time constraints
- Signal strength and execution risk

Its structure is sufficiently complex to expose weaknesses in:
- AST chunking
- Retrieval quality
- Prompt faithfulness

while remaining tractable within a 30-day, limited-time execution window.

---

### Constraints Acknowledged

- The repository choice is fixed for the duration of the project
- No mid-project switching to simplify scope
- Ingestion and chunking strategies must adapt to Flask’s structure, not vice versa

---

### Consequences

**Positive:**
- Results will generalize to real-world Python frameworks
- Demonstrates system-level thinking rather than toy experimentation
- High credibility for technical review or interviews

**Negative:**
- Increased complexity compared to smaller libraries
- Requires careful retrieval design to avoid partial-context hallucinations

---

### Review Trigger

This decision may only be revisited if:
- The repository proves technically impossible to process within defined constraints  
- A blocking incompatibility with AST parsing is discovered

Absent those conditions, this decision remains locked.
